# SINGULARITY

Five players. **One body.** A chaotic co-op physics party game: someone steers the head, someone works the arms, someone keeps the torso balanced, and two people each own a leg. Walk, climb, grab, throw — and try not to fall in the water.

Live game state—rooms, teams, roles, inputs, physics snapshots, round lifecycle—is browser-local temp state (tab memory, lost on reload). Only final leaderboard runs are durable, stored in **[SpacetimeDB](https://spacetimedb.com)** via a single `submitScore` reducer with the client-trusted clock.

## Architecture

```
┌─────────────────────────────┐         wss          ┌──────────────────────────────┐
│  Next.js 16 + React 19      │  ←────────────────→  │  SpacetimeDB module (TS)     │
│  Three.js + Rapier physics  │   leaderboard only   │  server/src/index.ts         │
│  (local room + simulation)  │   subscribe + submit │  leaderboard · submitScore   │
└─────────────────────────────┘                      └──────────────────────────────┘
```

- **`server/`** — SpacetimeDB server module written in TypeScript (`spacetime build`). Owns only:
  - **Global leaderboard** — client-submitted finishes land in a public, live `leaderboard` table. Each challenge has separate 3P/5P top-10 boards, so clients subscribe to a bounded data set instead of the full score history. Times are client-reported (trusted); only shape/bounds are validated.
- **`src/`** — the Next.js app. `src/game/local-room.ts` owns the ephemeral room (lobby, teams, roles, ready-up, countdown → playing → results); `src/game/net.ts` presents the same `Net` API to the game engine and syncs/submits the leaderboard through the generated SpacetimeDB bindings (`src/module_bindings/`, generated by `spacetime generate`).

## Repo layout

```
spacetime.json          points the CLI at ./server (local `singularity` database by default)
server/                 SpacetimeDB module (TypeScript)
src/                    Next.js app (game engine + UI)
src/module_bindings/    generated client bindings — do not edit
scripts/e2e.ts          end-to-end test for the module (leaderboard submit + validation)
```

## Develop

```bash
npm install                      # app deps
cd server && npm install && cd ..# module deps

spacetime start                                  # local SpacetimeDB on 127.0.0.1:3000
npm run spacetime:publish:local                 # publishes ./server as database "singularity" locally
npm run spacetime:generate                      # regenerate src/module_bindings after module changes
npm run dev                                      # http://localhost:3001 (Next.js on :3001; SpacetimeDB stays on 127.0.0.1:3000)
```

Copy `.env.example` to `.env`. The defaults already point at the local
SpacetimeDB (`ws://127.0.0.1:3000` / database `singularity`).

Run the module test suite:

```bash
npx esbuild scripts/e2e.ts --bundle --platform=node --format=esm --outfile=scripts/e2e.mjs
node scripts/e2e.mjs                       # uses .env (STDB_URI/STDB_DB) by default
```

Finishes are written to `leaderboard` with an explicit challenge and squad size. Times are client-reported; entries below 1 s, with unknown challenges, or with blank/team names outside 2–22 chars are ignored.

## Run locally

The database is permanently local — there is no cloud backend, and every
publish keeps existing data (the npm scripts pass `--delete-data=never`, so
republishing never wipes the leaderboard):

```bash
spacetime start                 # standalone SpacetimeDB on 127.0.0.1:3000
npm run spacetime:publish        # publishes ./server as database "singularity" locally, data preserved
npm run dev                      # Next.js frontend on http://localhost:3001; connects to ws://127.0.0.1:3000
```

> **Port note:** SpacetimeDB keeps port 3000; the `dev`/`start` npm scripts
> default the Next.js app to port 3001 (`next dev -p 3001`), so the two never
> fight for a port. Override with `npm run dev -- -p <port>` if you need
> something else.

The data lives in SpacetimeDB's data directory
(`C:\Users\<you>\AppData\Local\SpacetimeDB\data` on Windows,
`~/.local/share/spacetime` on Linux/macOS) and survives restarts. Backups are
a straight copy of that directory while the server is stopped.

The client connects to `ws://127.0.0.1:3000` and database `singularity`
by default (see `.env`); override with `NEXT_PUBLIC_SPACETIMEDB_URI` /
`NEXT_PUBLIC_SPACETIMEDB_MODULE` only if you move the local instance.
